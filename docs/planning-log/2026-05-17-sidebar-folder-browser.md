## 2. 가정 (Assumptions, §0.1)

명시하지 않으면 묵시적 가정이 빌드 중에 깨진다. 아래는 본 기획이 무너지면 함께 무너지는 가정이다.

1. **사용자는 "노트 폴더"를 본인이 관리한다.** Obsidian의 vault처럼 앱이 관리하는 단일 라이브러리는 도입하지 않는다 — 사용자가 Finder에서 만든 임의의 디렉터리들을 등록할 수 있어야 한다.
2. **사용자가 등록할 폴더 수는 평균 1~5개, 폴더당 `.md` 파일 수는 평균 50개 이내.** 1만 개 파일을 한 폴더에 두는 use case는 MVP에서 보장하지 않는다.
3. **현 시점 앱은 비-샌드박스(non-sandboxed)로 배포된다.** Mac App Store 배포 전환 시 security-scoped bookmarks 마이그레이션이 별도 과제(§11에 기록).
4. **파일 시스템 변경은 로컬 디스크에서만 발생한다.** iCloud Drive / Dropbox / 외부 동기화 시 FSEvents가 지연되거나 누락될 수 있음은 알려진 한계로 수용한다.
5. **사용자는 클릭한 파일을 "지금 작업 중인 창에서" 열기를 기대한다.** 클릭마다 새 창이 뜨는 것은 사이드바를 도입한 목적(빠른 탐색)에 반한다.
6. **`.md` 외 확장자(`.markdown`, `.txt`)는 MVP에서 비-노출.** Phase 2로 분리.

이 중 5번이 가장 무겁다 — ADR-0003(단일 창/단일 문서)을 폐기해야 성립한다. §4에서 상세 비교.

## 3. 성공 지표 (§0.2)

기능 나열 ≠ 성공. 아래 숫자가 움직여야 성공이다.

| 지표 | 목표 |
| --- | --- |
| **TTFF (Time to First File-Open via sidebar)** | 신규 사용자가 폴더를 1개 추가하고 파일을 처음 여는 데 ≤ 30초 (도움말 없이) |
| **사이드바 채택률** | 출시 후 14일 시점, 활성 사용자의 ≥ 60%가 세션당 사이드바 클릭 ≥ 1회 |
| **사이드바 vs. File>Open 비율** | 파일을 여는 행위 중 사이드바 경유 ≥ 75% (`File > Open`을 대체했는지 검증) |
| **외부 변경 반영 지연** | 외부에서 파일 추가/삭제 후 사이드바 트리 갱신까지 p95 ≤ 1초 |
| **회귀 지표** | 사이드바 도입 후에도 키 입력 반응 < 50ms (spec.md 비기능 요구 유지) |

측정 수단: `sidebar_opened`, `sidebar_folder_added`, `sidebar_file_clicked`, `file_opened{source: sidebar|menu|finder}` 이벤트 추가.

## 4. 옵션 평가 — 사이드바와 NSDocument의 동거 (§0.4)

핵심 충돌: NSDocument는 "파일 1개 = 문서 1개 = 창 1개" 모델. 사이드바에서 파일을 클릭하면 어디서 열리는가?

| 옵션 | 동작 | 장점 | 단점 | 평가 |
| --- | --- | --- | --- | --- |
| **A. 별도 브라우저 창** | 사이드바는 독립 창, 클릭 시 새 편집기 창 | NSDocument 모델 무수정 | 클릭마다 창이 늘어남 → 사이드바 도입 목적 자체를 해침 | ✘ 폐기 |
| **B. 편집기 창에 사이드바 + 클릭 시 새 창** | 모든 편집기 창이 같은 사이드바를 호스트, 파일 클릭 시 NSDocumentController가 새 창 열기 | 구현 단순, NSDocument 모델 유지 | 가정 5 위반. UX 목적과 어긋남 | ✘ 폐기 |
| **C. 편집기 창에 사이드바 + 인-플레이스 스왑 (권장)** | 단일 편집기 창이 사이드바 + 편집 영역의 split view. 파일 클릭 시 현재 창의 편집 영역에 문서 교체 | 사용자 기대(VS Code/Obsidian 패턴)에 부합. 빠른 탐색 가능 | ADR-0003 폐기 필요. "창=문서" 불변식 깨짐 → 미저장 변경 처리/Window restoration/Recent Documents 동작 재정의 필요 | ✅ 권장 |

**선택: Option C.** 근거: §3의 성공 지표(사이드바 채택률 60%, File>Open 대체율 75%)는 Option A/B로는 달성 불가하다. UX 목표가 아키텍처 제약을 우선한다. 단, ADR-0003을 명시적으로 폐기하고 새 ADR-0004(SplitViewController 기반 다문서-단일창)와 ADR-0005(Document lifecycle in shared window)를 신설해야 한다 — §10 참조.

타협안(예: "untitled + unmodified일 때만 인-플레이스 스왑, 아니면 새 창")은 의도적으로 거부한다. 두 가지 멘탈 모델을 동시에 유지하면 사용자가 어디서 열릴지 예측 불가 → §0.4에 따라 한쪽으로 결정.

## 6. 인스코프 / 아웃오브스코프

### In-Scope (MVP)
- 좌측 사이드바 영역 (NSSplitViewController 기반, 폭 조절·접기 가능)
- 사용자가 직접 추가한 폴더 목록 (다중, 각각 독립 루트)
- 폴더 추가 UI: 사이드바 헤더의 "+" 버튼 또는 `File > Add Folder…` 메뉴 → NSOpenPanel(디렉터리 선택)
- 폴더 제거 UI: 트리에서 폴더 루트 우클릭 → "Remove from Sidebar" (디스크 삭제 아님)
- 폴더 내부 재귀 트리 (서브폴더 + `.md` 파일). `.md` 외 확장자는 표시하지 않음 (단, 서브폴더는 안에 `.md`가 하나라도 있으면 표시)
- 파일 클릭 → 현재 창 편집 영역에 문서 로드 (미저장 변경 시 §7 플로우 적용)
- 실시간 갱신: 외부에서 파일/폴더 추가·삭제·이름변경·이동 시 트리 자동 반영 (p95 ≤ 1초)
- 등록 폴더 목록 영구 저장 (앱 재시작 후 복원)
- 사이드바 토글 (`View > Show/Hide Sidebar`, `⌘⌥S`)
- 모든 화면 상태 정의: 기본 / 비어있음 / 로딩 / 권한 거부 / 폴더 누락(이동·삭제됨) / 오프라인(외부 볼륨 분리) — §8 참조

### Out-of-Scope (의도적 제외)

| 항목 | 제외 이유 |
| --- | --- |
| 드래그&드롭으로 파일 이동/복사 | 핵심 가치 외. Phase 2 |
| 사이드바에서 rename / delete / new file | 핵심 가치 외. Finder로 우회 가능. Phase 2 |
| 검색 (파일명·내용 검색) | 별도 기능 (`⌘⇧O` 류). Phase 2 |
| 즐겨찾기/핀, 색상 라벨, 태그 | 가치 검증 전. Phase 3 |
| 이미지/PDF 등 비-md 파일 표시 | MVP 범위 한정. Phase 2 |
| iCloud/원격 동기화 충돌 해소 | OS·동기화 클라이언트 책임. 알림만 |
| 다중 편집 창 (사이드바 + 새 창 동시 운용) | ADR-0004에서 단일 창으로 결정. 멀티창은 Phase 3 |
| 다중 선택 / 비교 보기 / 분할 편집 | Phase 3 |

## 7. 사용자 플로우 (7단계 모델)

```
[1. 진입]
  앱 최초 실행 → 빈 새 문서 + 좌측 사이드바 (빈 상태 메시지: "Add a folder to get started")
  앱 재실행 → 마지막 등록 폴더 목록 복원, 마지막 열었던 문서 복원 (NSDocument restoration)

[2. 오리엔테이션]
  좌측: 사이드바 (등록 폴더 트리, 헤더에 + 버튼)
  우측: 편집기 (기존 spec.md SCREEN-01 그대로)
  스플리터 핸들: 사이드바 폭 조절, 더블클릭 시 토글

[3. 작업 — 폴더 추가]
  "+" 버튼 클릭 또는 File > Add Folder… (⇧⌘O)
  → NSOpenPanel (디렉터리 한정)
  → 폴더 선택 → 사이드바 루트로 추가, 즉시 펼침
  → FSEvents 구독 시작

[3'. 작업 — 파일 열기]
  사이드바에서 .md 파일 클릭
  → 현재 편집 영역 문서가 깨끗하면(unmodified): 즉시 교체
  → 미저장 변경이 있으면: 저장 확인 시트 (저장 / 저장 안 함 / 취소)
    → "취소" 선택 시 사이드바 선택 상태도 원래 파일로 되돌림
  → 새 문서가 로드되면 사이드바에서 해당 행 하이라이트

[4. 검토]
  사이드바와 편집기는 동일한 파일 상태를 표시 (●는 창 제목과 사이드바 행 양쪽에 표시)

[5. 커밋]
  ⌘S → NSDocument.save (기존 동작)
  저장 후 사이드바 행에서 ● 제거

[6. 피드백 — 외부 변경]
  외부에서 파일 추가 → 사이드바 트리에 새 행 등장 (애니메이션)
  외부에서 현재 편집 중인 파일 삭제 → 편집기 상단에 알림 바: "이 파일이 외부에서 삭제되었습니다. [다시 저장] [닫기]"
  외부에서 파일 내용 변경 + 편집기에서 미저장 변경 동시 존재 → 충돌 시트: "외부 변경 사항 / 내 변경 사항" 중 선택
  등록된 폴더가 외부에서 삭제됨/이동됨 → 트리 루트에 ⚠ 아이콘 + "Locate…" 버튼

[7. 재진입 / 복구]
  앱 재실행 → 폴더 목록 복원, 마지막 열린 문서 복원, 사이드바 펼침 상태 복원
  복원 대상 파일이 사라졌으면 → 빈 새 문서 + 사이드바 알림
```

### 체크포인트 (§0.5)

- 결정됨: Option C (인-플레이스 스왑), 폴더 다중 등록, `.md`만 표시, 비-샌드박스 배포 가정
- 사용자 검증 필요: TTFF 30초가 현실적인가? — 5명 모더레이션 테스트로 검증 (Phase 0)
- 여전히 가정: 외부 동기화(iCloud) 환경에서 FSEvents 신뢰도. 알파에서 측정.

## 8. 화면 명세 & 상태 정의 (§0.6 — 상태 누락 시 PRD 미완)

| 항목 | 내용 |
| --- | --- |
| 목적 | 등록 폴더와 `.md` 파일을 탐색하고 즉시 열기 |
| 진입 조건 | 앱 실행 (기본 표시), `View > Show Sidebar` |
| 주요 콘텐츠 | 헤더(타이틀 "Folders" + "+" 버튼), 트리(NSOutlineView), 빈 상태 CTA |
| 기본 CTA | 폴더 추가 |
| 보조 액션 | 행 클릭(열기), 디스클로저(펼침/접기), 우클릭 컨텍스트 메뉴 |

**필수 상태 정의 — 누락 시 PRD 미완 (§0.6):**

| 상태 | 조건 | 표현 |
| --- | --- | --- |
| 기본 | 폴더 ≥ 1 등록, 정상 접근 | 트리 정상 표시 |
| 비어있음 | 등록 폴더 0개 | 중앙 정렬 placeholder + "Add Folder…" 버튼 |
| 로딩 | 큰 폴더 첫 스캔 중 | 노드 옆 spinner, 200ms 이상일 때만 노출 (그 이하는 즉시 채움) |
| 권한 거부 | 폴더에 읽기 권한 없음 | 루트 행에 🔒 아이콘 + "권한이 없습니다. 시스템 설정에서 권한을 부여하세요." 툴팁 |
| 폴더 누락 | 등록된 폴더가 디스크에서 사라짐 | 루트에 ⚠ + "찾을 수 없음" + [Locate…] [Remove] 버튼 |
| 오프라인 | 외부 볼륨에 있는 폴더가 마운트 해제됨 | 폴더 누락과 동일 처리 (Locate 대신 [Reconnect]) |
| 큰 폴더 경고 | 단일 폴더에 `.md` 파일 ≥ 1,000개 | 루트에 ℹ 아이콘 + "표시할 항목이 많아 일부만 로드됨" (지연 로딩) |
| 에러 (FSEvents 구독 실패) | 시스템 한계 초과 등 | 행 표시는 유지, 헤더에 "자동 갱신 중지됨 [재시도]" |

### SCREEN-01 (기존) — 갱신

- 좌측 영역에 SCREEN-03 추가. 편집 영역 자체는 변경 없음.
- 창 제목 = 현재 편집 중인 문서 파일명 (기존 그대로). 사이드바의 선택 행과 동기화.

### SCREEN-04: 저장 확인 시트 (사이드바로 인한 문서 교체 시)

기존 SCREEN-02(닫기 전 경고)와 동일한 UI, 진입 조건만 추가: "사이드바에서 다른 파일 클릭 시 현재 문서에 미저장 변경 존재".

## 9. 인수 기준 (의도 명시, §0.3)

각 기준은 "왜 이 동작이 중요한가"를 함께 명시한다. 단순 동작 검증은 채택하지 않는다.

### AC-04: 폴더 추가

```
시나리오 1 — 첫 폴더 추가:
  Given 등록된 폴더가 0개인 사이드바
  When  사용자가 "+" 버튼 클릭 → NSOpenPanel에서 폴더 선택 → "Open"
  Then  사이드바 루트에 폴더가 추가되고, .md 파일/서브폴더가 펼쳐진 상태로 표시됨
  And   다음 앱 실행 시에도 동일하게 복원됨
  Why   §3의 TTFF ≤ 30초 달성을 위해서는 첫 폴더 추가가 단일 액션 흐름이어야 한다

시나리오 2 — 잘못된 항목 선택:
  Given NSOpenPanel
  When  사용자가 파일(폴더 아님)을 선택 시도
  Then  "Open" 버튼 비활성 (canChooseFiles=false)
  Why   잘못된 선택을 사후 오류로 처리하는 대신 선험적으로 차단해야 인지 부담 감소
```

### AC-05: 파일 열기 (인-플레이스 스왑)

```
시나리오 1 — 미저장 변경 없는 상태에서 다른 파일 클릭:
  Given 편집기에 unmodified 문서 표시 중
  When  사이드바에서 다른 .md 파일 클릭
  Then  편집 영역이 즉시 새 파일로 교체됨 (시트/다이얼로그 없이)
  And   사이드바 선택 하이라이트가 새 파일로 이동
  Why   사이드바의 핵심 가치는 마찰 없는 탐색이다. 변경이 없으면 확인을 묻지 않는다

시나리오 2 — 미저장 변경 있는 상태에서 다른 파일 클릭:
  Given 편집기에 ● 표시된 문서
  When  사이드바에서 다른 파일 클릭
  Then  "저장하시겠습니까?" 시트 표시 (저장/저장 안 함/취소)
  And   "취소" 선택 시 사이드바 선택은 원래 파일로 되돌아감
  Why   §0.6의 "사용자의 작업 손실은 침묵해서는 안 된다". 클릭 한 번에 작업이 사라지면 신뢰가 깨진다

시나리오 3 — 동일 파일 재클릭:
  Given 편집기에 X 파일 표시 중
  When  사이드바에서 X 파일 다시 클릭
  Then  아무 동작 없음 (재로드하지 않음)
  Why   외부 변경 반영은 §6의 충돌 처리로 별도로 다룬다. 단순 재클릭이 사용자 작업을 덮어쓰면 안 된다
```

### AC-06: 실시간 갱신

```
시나리오 1 — 외부에서 파일 추가:
  Given 등록 폴더 F에 a.md, b.md가 표시 중
  When  Finder에서 F에 c.md 생성
  Then  사이드바에 c.md 행이 p95 1초 이내 등장 (정렬 위치 유지)
  Why   "실시간으로 수정되면 업데이트" — 요청 핵심. 폴링이 아닌 이벤트 기반이어야 50ms 키입력 예산 보호

시나리오 2 — 외부에서 폴더 이름 변경:
  Given 등록 폴더 F가 트리에 표시
  When  Finder에서 F를 G로 rename
  Then  사이드바 루트가 G로 갱신, 하위 항목 유지
  And   현재 편집 중인 파일 경로도 자동 갱신 (NSDocument fileURL 추적)
  Why   외부 작업과 앱 상태의 진실 단일화

시나리오 3 — 외부에서 현재 편집 중인 파일 삭제:
  Given 사용자가 X.md를 편집 중 (미저장 변경 ●)
  When  Finder에서 X.md 삭제
  Then  편집기 상단에 비-모달 알림: "이 파일이 외부에서 삭제되었습니다."
  And   사이드바에서 X.md 행 제거
  And   편집기는 닫히지 않음 (사용자 작업 보호 — 다른 이름으로 저장 가능)
  Why   가정 4(외부 동기화)에서 흔한 시나리오. 침묵 종료는 작업 손실로 이어진다
```

## 10. 아키텍처 영향

상세 설계는 별도 architecture 작업이 처리하지만, 이 기능이 건드릴 결정 사항을 미리 표면화한다.

### 폐기

- **ADR-0003 (단일 창 / 단일 문서)** → 폐기. 사유: §4 Option C 채택.

### 신설 (제안)

- **ADR-0004: SplitViewController 기반 사이드바 + 인-플레이스 스왑**
  - 결정: `EditorWindowController`가 `NSSplitViewController`를 호스트. Left pane = `SidebarViewController`, Right pane = 기존 `EditorViewController`.
  - 결과: 창 1개 = 사이드바 1개 + 활성 문서 1개. 클릭 시 `EditorViewController`가 `MarkdownDocument`를 swap.
  - 미저장 변경 처리: `swapDocument(to:)` 호출 시 현재 `document.canClose(...)` 흐름을 재사용 → AC-05 시나리오 2.

- **ADR-0005: 사이드바 모델 — 폴더 등록 + FSEvents 구독**
  - 결정: 신설 `FolderBookmarksStore` (UserDefaults 영속) + `FolderWatcher` (FSEvents 래퍼).
  - 결과: Document Layer는 변화 없음. 신규 `sidebar/` 모듈이 Infrastructure Layer 옆에 위치.
  - 제약: 비-샌드박스 가정(가정 3). 샌드박스 전환 시 `URL.bookmarkData(options: .withSecurityScope)`로 마이그레이션 필요.

### 폴더 구조 추가 제안

```
Sources/
  sidebar/
    SidebarViewController.swift     — NSOutlineView 호스트
    SidebarDataSource.swift          — 트리 모델 (FolderNode/FileNode)
    FolderBookmarksStore.swift       — UserDefaults 영속 + (향후) security-scoped bookmark
    FolderWatcher.swift              — FSEvents 래퍼, debounce 200ms
    SidebarCommands.swift            — Add Folder…, Remove from Sidebar, Reveal in Finder
```

### 의존성 규칙 (유지)

- `sidebar/` → `document/`(MarkdownDocument 인스턴스 생성을 위해 NSDocumentController 사용)는 허용
- `sidebar/`는 `editor/`를 import하지 않음 — 통신은 NotificationCenter 또는 WindowController 위임으로
- `document/` / `infrastructure/`는 `sidebar/`를 모름 (위 → 아래 의존 규칙 유지)
