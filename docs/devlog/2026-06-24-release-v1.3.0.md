## 결정

### export 전용 — 읽기(import)·`.doc`·Google Docs 제외
마크다운은 표현력이 좁아 docx/hwpx 왕복(round-trip) 시 표·각주·서식 손실이 불가피하다. import를 넣으면 "열었다 저장하면 망가지는 앱"이 되는 위험이 가장 크다. `.doc`(OLE 바이너리)·Google Docs(네트워크 동기화)는 앱 성격을 바꾸므로 후보에서 제외.

### 순수 Swift Writer 직접 작성 (의존성 0)
Pandoc 번들은 hwpx 미지원에 앱이 무거워지고, 네이티브 `NSAttributedString` docx export는 서식 통제가 약하고 hwpx와 코드를 공유하지 못한다. 두 포맷이 같은 IR을 공유하고 배포가 가벼운 순수 Swift Writer를 택했다.

### hwpx 1차 범위 — 표 평탄화·이미지 생략
OWPML에서 표(`hp:tbl`)·이미지(`hp:pic`+BinData)는 가장 복잡한 요소라, 1차에 완전 구현하면 한글이 안 여는 리스크가 크다. 1차는 **텍스트 풀 충실도**에 집중하고, 표는 행별 텍스트로 평탄화(내용 보존, 격자는 후속), 이미지는 생략 + 건너뜀 경고로 둔다. docx는 표·이미지 모두 완전 지원하므로 hwpx만의 1차 제약이다.

### 실제 hwpx 샘플로 구조 복제
OWPML을 기억으로 재구성하면 한글이 거부할 위험이 크다. 로컬의 실제 hwpx 산출물을 압축 해제해 네임스페이스·charPr/paraPr/borderFill 스키마·섹션 설정을 그대로 복제했다. 이 덕에 첫 시도에서 한글이 열렸다.
